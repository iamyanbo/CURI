# Handoff — pi-autoresearch

Written 2026-08-22 for whoever picks this up next. Two parts: **what exists and
works today**, and **what to build for the Google hackathon**, which is largely
"detach from Pi and local hosting, move to Google Cloud".

Read `README.md` first for what the system is. Read `SCOPE.md` for what it
honestly does and does not enforce. Read `plans/06-findings.md` for the defect
history — much of it will save you from repeating a mistake.

---

# Part 1 — What exists

## The idea in one paragraph

An automated research harness that tries to disprove its own results. A campaign
proposes a hypothesis, implements it, measures it with an evaluator the candidate
cannot see, and judges it with a pure function no model can reach. Thresholds are
registered *before* the experiment runs. Negative results are kept. Only claims
that survive multi-seed replication against a held-back measurement may advance
the baseline.

## What has actually been run

| campaign | domain | result |
|---|---|---|
| `tinyml-001` | char-LM, bits-per-char, CPU | ~80 cycles, several validated improvements |
| `cuda-001` | softmax CUDA kernel, GB/s | 264 → 373 GB/s, 3 validated claims, 5/5 planted cheats caught |
| `finance-001` | backtest, Sharpe | 125 cycles, **0 validated claims** (correct outcome), causality probe caught 3 real lookahead attempts |
| `attention-001` | fused attention CUDA, TFLOP/s | running; domain was **generated by an agent**, not hand-written |

Two promotions were **withdrawn** after audit, both recorded in the ledger rather
than edited out. Both had cleared thresholds that were below the measured noise
floor. That defect is now closed by a gate.

## Architecture

```
src/loop/campaign.ts     driver: calibration, cycles, replication, baseline advance
src/loop/cycle.ts        one cycle: MANAGE → REGISTER → EXECUTE → CLASSIFY →
                         RUN → EVALUATE → JUDGE → SEAL
src/loop/judge.ts        PURE function. No model can set a status.
src/loop/portfolio.ts    lane allocation + stop policy
src/loop/calibrate.ts    measures the noise floor before any research
src/core/harness.ts      the only bridge between the loop and a domain
src/domain/*             DomainAdapter: metric, replication kind, cost, cheats
src/worker/pi-worker.ts  spawns the Pi CLI as a subprocess  ← THE THING TO REPLACE
src/store/*             SQLite, hash-chained event log
src/ui/*                read-only dashboard + SSE
src/doctor.ts            verifies a domain mechanically before it may run
src/setup.ts             agent that writes a whole domain from one prompt
```

**The loop never imports a domain.** Everything field-specific arrives through
`DomainAdapter`. That is why CUDA → finance needed exactly one core change.

## The properties worth protecting

Do not let these move into a model, a framework, or the cloud control plane:

1. **The judge is a pure function.** No model can set a status.
2. **Contracts are pre-registered.** Hashed and stored before the worktree exists;
   the judge refuses a contract registered after its result.
3. **The evaluator is protected.** Candidates cannot read or write
   `.autoresearch-protected/`. Its hash is checked each cycle.
4. **The noise floor is measured, never declared.** The campaign re-runs its own
   baseline across replication variants first. Thresholds below it are rejected
   at validation. This exists because a guessed floor let a baseline advance on
   noise.
5. **Fixtures are permanent.** When a domain proves porous, add a fixture; never
   loosen a check.
6. **Negative results are retained.** Refutations and null results are the
   product, not waste.

## Things that took a long time to learn

- **Measure, don't declare.** Every hand-entered constant was wrong: noise floors
  (0.15 vs measured 2.18 in finance; 8 vs 10.6 in CUDA), baselines, tolerances.
- **A defence that has never fired is indistinguishable from one with nothing to
  catch.** Two detectors were silently dead for a whole campaign. `verify-cheats`
  and `doctor` exist because of that.
- **Misleading output is a defect.** Roughly a third of the defect list is the
  harness saying something untrue about its own state — `0 tok · absent` for a
  stage with no agent, `repeated_infrastructure_failure` when the infrastructure
  was working, a correctness check quoting a *passing* number as its reason for
  failing. Fix the message, not just the behaviour.
- **A running process holds the code it started with.** A fix on disk is not a
  fix in the campaign. One false baseline advance happened in exactly that gap.

## Known open items

- `INTERVENTION_HAD_NO_EFFECT` may fire from timer quantisation rather than real
  no-ops on this GPU; unverified.
- The generated attention evaluator has `ROOFLINE_TOLERANCE = 4.0` (CUDA uses
  1.05). Defensible for tensor cores, but weak as a fraud gate. Tighten or
  require explicit opt-in.
- Baseline vs candidate are compared across *different* replication variants in
  temporal-fold domains. Should compare like-for-like per window.
- `plans/06-findings.md` stops at 26 defects; ~10 more are documented only in
  commit comments and this file.

# Part 2 — The hackathon build

## Requirements

1. Gemini 3.5+ via **Gemini API or Vertex AI**
2. At least one **Google agent framework** — ADK, GenAI SDK, Antigravity SDK, GenKit
3. At least one **Google Cloud infrastructure service** — Cloud Run, Cloud SQL,
   Firestore, GKE, Pub/Sub

## The honest problem to solve

A cloud dashboard over a locally-running campaign satisfies the letter of #3 and
nothing else — the meat of the project would still be local. The owner rejected
that, correctly. **Aim for the whole pipeline in Google Cloud.**

## Target architecture

```
Cloud Run Job (NVIDIA L4)   campaign loop, nvcc, experiments
Cloud Run service           dashboard, public URL
Firestore                   campaign state / evidence
Pub/Sub                     replication jobs fanned out to workers
Vertex AI                   Gemini 3.5
Genkit                      manager + executor agents
```

### Why this is not a checkbox

**Replication is the weakest part of the system today.** All 3–4 replications run
sequentially, on one machine, one GPU, one environment — sharing every confound.
`SCOPE.md` already states the gap: *A5 requires independent external
reproduction*, and the ladder caps at A3. Fanning replication out to independent
Cloud Run workers is that missing rung: different machine, cold process, fresh
environment. It also runs in parallel, which matters because replication is the
slowest step.

**Cloud GPU is better hardware for this, not just remote hardware.** An L4 has
24 GB VRAM against ~1.4 GB free on the owner's 3060 Ti, and datacenter GPUs hold
stable clocks. Local measurement noise was 10.6 GB/s largely from boost/throttle;
a tighter floor means smaller real improvements become detectable. The roofline
check already self-calibrates via `cudaGetDeviceProperties`, so it adapts to
whatever GPU it lands on with no code change.

### Detaching from Pi

`src/worker/pi-worker.ts` is the seam. Everything model-facing goes through:

```ts
runPiWorker({ role, prompt, tools, model, timeoutMs }) → { text, trace, usage }
```

called from exactly three places: `cycle.ts:231` (manager), `cycle.ts:401`
(executor), `setup.ts:167` (setup agent). Write `genkit-worker.ts` against the
same contract and nothing downstream changes.

**Do the manager first.** It is pure reasoning, no file tools, returns one JSON
object — and calibration measured a **22% manager failure rate** from empty or
prose-wrapped responses, each costing a cycle. Genkit's schema-enforced output
removes that failure class structurally.

**The executor is harder and should come second.** It gets
`read/write/edit/grep/find/ls/bash` from Pi for free, and runs as a *separate
process*. On Genkit those tools must be reimplemented and run in-process — weaker
isolation for the one agent that edits files and runs shell commands. In a
container that matters less (the container is the sandbox), but be deliberate
about it rather than sliding into it.

Keep Pi behind a `--worker pi|genkit` flag so a demo failure is recoverable.

### Suggested order

1. **Request Cloud Run GPU quota today.** Region-limited, approval is not
   instant, and it is the long pole. Everything else can be built while waiting.
2. **Genkit manager**, behind a flag, tested locally against `domains/cuda.domain.json`.
3. **Container**: `nvidia/cuda` base + Node 22 + Python + nvcc. Verify `doctor`
   passes inside it — that is the whole point of `doctor`.
4. **Firestore state.** The event log is already append-only and hash-chained,
   which maps cleanly. Keep the chain verification.
5. **Cloud Run Job** for the campaign; **Cloud Run service** for the dashboard
   (it must bind `0.0.0.0`, not `127.0.0.1`).
6. **Pub/Sub replication fan-out** — the piece that makes cloud load-bearing.
7. **Genkit executor** last, if time allows.

### Costs, measured not guessed

Per cycle: ~15K input, ~6K output tokens. An 8-hour overnight run ≈ 160 cycles ≈
2.4M in / 1M out.

| item | per overnight run |
|---|---|
| Cloud Run Job, L4, 8h | $6–9 |
| dashboard + Firestore | ~$0 at this volume |
| Gemini, Flash-class | ~$1–3 |
| Gemini, Pro-class | ~$10–20 |

Two notes. Cycles are **output-heavy** (the executor writes code), and output
tokens cost several times input — running the manager on a Pro-tier model and the
executor on Flash gets most of the reasoning quality far cheaper, and the harness
already supports different models per role. And the GPU is idle ~97% of the time
while agents think; dispatching only experiments to the GPU would remove most of
that line item, at the cost of more architecture.

Make the job **shut its own instance down** when the campaign stops. The stop
conditions already exist; an idle GPU left running for days is the only way this
gets expensive.

### What to demo

The pipeline is not the story. **The system catching cheating is.** Strongest
material:

- The **roofline** check: a kernel claiming 478 GB/s on a 448 GB/s bus is proof,
  not suspicion.
- The **causality probe** in finance: perturb the future, check the past did not
  move. Catches lookahead with no `shift(-1)`, no negative index — the form real
  backtest overfitting takes, and undetectable by code review.
- The **withdrawn promotions**: the system produced a false positive, an audit
  caught it, and the correction was written *into* the ledger rather than edited
  out.
- **`setup.ts` generating a whole domain from one sentence**, then being refused
  by `doctor` until its own evaluator caught its own planted cheats.

## First commands

```bash
npm install
npx tsx src/cli.ts status --campaign attention-001    # what is running now
npx tsx src/ui/server.ts                              # dashboard on :4791
npx tsx src/doctor.ts --domain domains/cuda.domain.json   # verify a domain
npx tsx src/setup.ts "your research task"             # generate a new one
```

`attention-001` is running locally as of this handoff. Stop it with
`npx tsx src/cli.ts stop --campaign attention-001` or the dashboard button.
